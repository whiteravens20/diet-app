## External-source recipe importer (Phase F of the curation-queue plan)

**Provenance.** Listed as Phase F in the curation-queue implementation
plan and deferred there with the reasoning below. ADR-0008 references
the same deferral under "Why not (alternatives)". This entry is the
durable home for the design so neither the plan file nor the ADR has to
carry it.

**Goal.** Pull recipes from a public CC-licensed external source
(TheMealDB ~300 recipes is the obvious first candidate; RecipeNLG /
Open Recipe Format / others sized similarly), normalise units, slug-map
against the live `Ingredient` table, and write them as
`DraftSource = EXTERNAL` rows in the existing `RecipeDraft` table. From
there they flow through the **same** review + ship pipeline as AI
drafts: human approval, engine-recomputed nutrition, PR ship.

**Why it's deferred (not killed).**

- The AI recipe generator (Phase D, shipped) already produces unbounded
  supply at first-class EN + PL quality. It's not gated by an external
  dataset's coverage.
- TheMealDB is mostly American / British comfort food with EN-only
  steps. Every imported row would need a PL translation pass before
  shipping — doubling the per-row workflow versus a multi-locale AI
  draft.
- Slug-mapping is the hard part: external recipes use free-text
  ingredient strings ("1 onion, finely chopped") that need normalisation
  against our slug table. Unresolvable strings ⇒ rejected drafts; high
  rejection rate ⇒ low ROI per dev-day spent on the mapper.
- License surface is wider: each source has its own attribution
  requirements that have to land in the draft's `provenanceUrl` /
  `provenanceLicense` columns and propagate through the shipped JSON
  into the rendered recipe.

**Trigger to build.** The curated set crosses ~500 recipes and the queue
runs dry — i.e. the operator is generating fewer AI batches than the
reviewers can drain — and the missing variety is identifiably the kind
external comfort-food datasets cover well. Without that signal, AI
generation + ingredient-name overrides + staple curation are the higher-
leverage paths.

**Scope when picked up.**

- New module `apps/api/src/admin/drafts/external/` mirroring the AI
  drafts module's runner / validator / single-flight pattern.
- Source-specific adapters (`themealdb.adapter.ts`, …) behind a
  common `ExternalRecipeSource` interface. Adapters fetch + normalise
  to a neutral intermediate shape; the rest of the pipeline is shared.
- Slug-mapper: fuzzy match against `Ingredient.slug` with a per-source
  override file at `apps/api/src/admin/drafts/external/slug-overrides.<source>.json`
  for known aliases. Unresolvable rows are rejected with reason
  persisted, never reach the human.
- License metadata threaded end-to-end: `RecipeDraft.provenanceUrl` +
  `provenanceLicense` already exist in the schema (added in Phase B for
  this exact purpose); writers propagate them into
  `data/recipes/<batchId>.json` so the rendered recipe can credit the
  source.
- PL translation pipeline: imports land EN-only by design (no AI in the
  import path); a follow-up runner pass uses the existing AI translation
  runner from ADR-0007 to fill missing locales before ship. Decoupling
  keeps each step inspectable.
- Admin UI: a third tab in `/admin/curation` ("External imports")
  alongside Recipes and Ingredient names. Per-source "Import N from
  TheMealDB" button with the same single-flight job pattern.

**Out of scope even at v1.1.** Live syncing (one-shot import + edit is
enough — drift back to the source isn't a feature anyone asked for);
multi-source bulk merging of conflicting versions of the same recipe;
any source that doesn't allow redistribution under CC-BY-SA or similar.

**Sizing estimate.** ~3–4 dev-days for the first adapter (TheMealDB)
including the slug-mapper, license plumbing, and admin tab. Each
additional source after that is ~½ day if the adapter contract holds.
