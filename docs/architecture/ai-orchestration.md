# AI Orchestration

AI is an **optional assistant**, never a source of truth and never a hard dependency.
Code lives in [`apps/api/src/ai`](../../apps/api/src/ai).

## The contract with AI

AI **may**: draft recipe structure, suggest substitutions, propose plan variations,
explain trade-offs in plain language.

AI **may not**: produce nutrition numbers, ignore allergens/diet constraints, or use
ingredients absent from the curated database. Everything it returns passes the
deterministic validation layer.

## Provider abstraction

`AiProviderAdapter` (`provider.interface.ts`) is one interface: `chat(messages, opts)`.
Four adapters implement it:

| Provider | Adapter | Notes |
|---|---|---|
| OpenAI | `OpenAiProvider` | Chat Completions. |
| Anthropic | `AnthropicProvider` | Messages API; `system` handled separately. |
| OpenRouter | `OpenRouterProvider` | OpenAI-compatible; routes many models. |
| Ollama | `OllamaProvider` | Local, no API key; the self-hosted default. |

## Routing & failover

`AiRouterService.chat()`:

1. `AiKeyService.resolveChain(userId)` builds the failover chain — the user's enabled
   providers (by `priority`), then admin defaults.
2. Each provider is tried in order. A retryable failure (429 / 5xx / connection) moves
   to the next; the attempt is recorded in `AiUsageLog`.
3. If the whole chain is exhausted (or empty), the router returns `text: null` and the
   caller falls back to the deterministic engine.

Every routed result carries `AiGenerationMeta`: which provider served it, the
`failoverChain`, `usedDeterministicFallback`, and any rejected/remapped ingredients.

## Key storage

Per-user keys are encrypted with **AES-256-GCM** (`crypto.ts`) using
`AI_KEY_ENCRYPTION_SECRET`. Ciphertext (`iv:tag:data`) is stored in
`AiProviderConfig.encryptedKey`; plaintext is decrypted only in-process at call time.
The API never returns keys — the DTO exposes only `hasKey`.

## Validation layer

`AiValidationService.validateIngredients()` enforces the AI contract:

1. Each AI-drafted ingredient name is matched to a curated `Ingredient` (exact →
   case-insensitive → fuzzy). No match → **rejected**. Different match → **remapped**.
2. Nutrition is **recomputed** from the matched ingredients via the engine
   (`toCanonical` + `nutritionFor`) — AI's numbers are discarded.
3. The result reports `rejected[]` and `remapped[]` so the UI is transparent.

## Deterministic fallback

When no provider is usable, the deterministic engine serves the same features:

- **Meal generation** — the optimiser over curated + template-composed recipes.
- **Substitutions** — `substituteIngredient` (calorie-preserving, constraint-checked).
- **Shopping lists / calorie math** — always deterministic; AI is never involved.

The fallback recipe library is generated by the **template composition engine**
(`recipe-templates.ts`) — see [algorithms.md](algorithms.md). The app is therefore fully
usable with no AI key configured at all.

## Ollama integration

Ollama is the recommended path for fully self-hosted, key-free AI. The admin sets
`OLLAMA_BASE_URL` (the compose `ollama` service by default) and `AI_DEFAULT_PROVIDER=ollama`.
GPU acceleration: layer `infra/docker-compose.gpu.yml` (NVIDIA Container Toolkit). Pull
models into the container, e.g. `docker compose exec ollama ollama pull llama3.1:8b`.
Suggested models: Llama, Mistral, Gemma, DeepSeek, Qwen.

## Prompt engineering

AI prompts are **constrained generation**: the system prompt supplies the allowed
ingredient list, the calorie/macro target, and the diet/allergen constraints, and asks
for **structure only** (titles, steps, ingredient names + quantities) as JSON. The model
is explicitly told not to emit nutrition values. The validation layer is the safety net —
prompts reduce rejected ingredients but never replace validation. Keep prompt templates
versioned alongside the code that builds them so changes are reviewable.
